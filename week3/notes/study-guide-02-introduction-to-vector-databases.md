## 1. What a vector database is (and why normal DBs fail)

### 📄 FROM THE PDF
> **Introduction to Vector Database**
> In today's data-driven world, the need for sophisticated systems to handle **unstructured** and **high-dimensional data** is skyrocketing. Vector Databases — is what enables these things. Whether you're working with image embeddings, text representations, or multimodal data, vector databases provide the backbone for fast, efficient, and scalable similarity search and retrieval. But what makes them so special? Let's find out!
>
> **What is a Vector Database?**
> A vector database is a specialized data storage system designed to handle high-dimensional vectors. In the realm of AI, vectors often represent data points in numerical form, such as embeddings generated by machine learning models. These embeddings capture semantic meaning, enabling operations like similarity search. Traditional databases struggle with high-dimensional data due to their inherent complexity and the computational overhead of similarity queries. Vector databases, however, are optimized to store, index, and query such data efficiently.

### 🧠 EXPLAINED
A **vector database** is a datastore purpose-built to answer *one* kind of question extremely fast: **"which stored vectors are closest to *this* query vector?"** That's it. It stores embeddings (the meaning-as-numbers vectors from W2·SG03) and finds nearest neighbors — at scale, in milliseconds.

Let's unpack the two words the PDF leans on:

> 🔑 **Unstructured data** = data with no fixed rows-and-columns schema: free text, images, audio, video. The opposite of the neat tables an RDBMS was built for. 💻 The stuff you'd normally shove into a `BLOB` and give up on querying by *content*.
> 🔑 **High-dimensional vector** = a vector with hundreds or thousands of numbers (e.g. OpenAI embeddings = 1,536 dims). "Dimension" = the length of the list. Each embedding is a single point in a 1,536-D space.

> 💻 **What's a `BLOB`?** **B**inary **L**arge **OB**ject — a database column type for storing a whole *file's worth of raw bytes* directly in a row: an image, a PDF, an audio clip, a big chunk of text. In Java it maps to a `byte[]` / `java.sql.Blob`. (`TEXT`/`CLOB` are the same idea for large *text*.) The catch — and the reason it's mentioned here — is that a traditional DB can store a BLOB but **can't search by what's *inside* it.** It can find the row by its structured labels (`WHERE title = 'Refund Policy'`) but has no way to answer *"find docs that **talk about** refunds"* or *"images that **contain** a cat."* The BLOB is an opaque sealed box: the DB sees the label on the outside, never the contents. So "shove into a BLOB and give up on querying by content" = you can *store* the rich data but you've *surrendered the ability to search it by meaning.* **That surrender is exactly what a vector database undoes:** embed the content → store the vector → now you *can* query by meaning. (Traditional: `image → BLOB → 🔒 find by filename only`. Vector DB: `image → embedding → 🔓 find by what's in it`.)

**The core question: why can't I just use PostgreSQL / MySQL?** This is the heart of the reading, and the PDF states it but doesn't explain *why*. Here's the real reason:

A traditional database index (a **B-tree**) is built for **exact and range lookups on scalar values** — `WHERE id = 42`, `WHERE age BETWEEN 20 AND 30`. It works by keeping values *sorted*. But "similarity" isn't a sortable scalar — it's a **distance in 1,536-dimensional space.** There's no single axis to sort on. To find the closest vector the naive way, you'd have to **compute the distance from your query to *every single stored vector*** and keep the smallest — a full table scan, every query.

💻 **The backend analogy that makes it click.** You already know this pattern from *text search*. Nobody runs `WHERE description LIKE '%wireless headphones%'` at scale — a `LIKE '%...%'` can't use a B-tree index, so it scans every row. That's why we reach for **Elasticsearch / Lucene** with an **inverted index** built *specifically* for text matching. A **vector database is the exact same move, one level up**: a specialized store with a specialized index, built for *similarity* search instead of *keyword* search. `LIKE` → Elasticsearch is *keyword* → semantic. Same architectural instinct: when the query pattern doesn't fit a B-tree, you build a purpose-built index.

So the one-line definition to keep: **a vector DB = "Elasticsearch for meaning" — a store whose whole reason to exist is fast nearest-neighbor search over embeddings.**

## 2. Why vector DBs are suddenly everywhere

### 📄 FROM THE PDF
> **Why Are Vector Databases Gaining Popularity?**
> 1. **Explosive Growth of AI Applications:** From recommendation systems to generative AI, modern applications rely on embeddings to understand user intent, image contents, or even audio patterns.
> 2. **Scalability and Speed:** Imagine searching for a visually similar image or retrieving documents related to a query in milliseconds — vector databases make this a reality.
> 3. **Versatile Use Cases:**
>    - **Search Engines:** Powering semantic search where the focus is on meaning rather than exact matches.
>    - **Recommendation Systems:** Serving personalized content by comparing user preferences represented as vectors.
>    - **Chatbots:** Enabling conversational AI to fetch contextually relevant responses.

### 🧠 EXPLAINED
The through-line: **once you represent things as embeddings, almost every "find me things like this" problem becomes the same problem** — nearest-neighbor search. The vector DB is the shared engine underneath all three use cases:

| Use case | What's embedded | What "nearest neighbor" means |
|---|---|---|
| **Semantic search** | Documents + the query | Docs whose *meaning* matches the query (not keywords) |
| **Recommendations** | Users, products, past behavior | Items near a user's taste vector ("people/products like you") |
| **Chatbots (RAG!)** | Knowledge-base chunks + the question | The chunks that answer the question — *this is SG01's retrieve step* |

Notice the third row: **"Chatbots — fetch contextually relevant responses" is literally the retriever from SG01.** The vector DB is what makes RAG's step ② possible. Recommendations and search are the *same machinery* pointed at different embeddings — which is exactly the "scalability across domains" advantage SG01 highlighted: swap what you embed, keep the engine.

💻 **Why *now*?** Embeddings existed for years, but three things converged: (1) LLMs and models like CLIP made *high-quality* embeddings cheap and easy to generate; (2) the RAG pattern created massive demand for fast retrieval; (3) datasets grew to millions/billions of vectors, past what a brute-force scan can handle. The vector DB is the piece of infrastructure that shift *required.*

## 3. The four key components

### 📄 FROM THE PDF
> **Key Components of a Vector Database**
> 1. **Vector Storage:** Vectors are stored efficiently, enabling quick access during queries.
> 2. **Indexing:** Techniques like **Approximate Nearest Neighbor (ANN)** search reduce computational overhead by focusing on approximate rather than exact matches.
> 3. **Querying:** Vector databases support queries like "Find all vectors similar to X," often using distance metrics like **cosine similarity** or **Euclidean distance**.
> 4. **Scalability:** They handle millions (or even billions) of vectors with ease, ensuring performance doesn't degrade as the dataset grows.

### 🧠 EXPLAINED
These four map cleanly onto what any storage system does — *store, index, query, scale* — but each has a vector-specific twist:

1. **Vector Storage** — the raw embeddings on disk/RAM, usually alongside **metadata** (the original text, a doc id, tags, dates) and an id. 💻 Think of each record as `{ id, float[] vector, payload }` — the vector is *what you search by*, the payload is *what you return*.

2. **Indexing** — the special sauce. Rather than compare the query to *every* vector (exact but slow), the DB builds an **ANN index** that finds *almost* the closest vectors while skipping the vast majority of comparisons. This is [§5](#5-ann--indexing-the-trick-that-makes-it-fast-hnsw) — the single most important idea in the reading.

3. **Querying** — the operation is always some flavor of *"top-K nearest to this query vector"* (top-K from SG01!), scored by a **distance metric** — [§4](#4-distance-metrics-how-similar-is-measured).

4. **Scalability** — staying fast from thousands to *billions* of vectors. This is *why* ANN exists: exact search scales linearly (2× data → 2× slower), which is fatal at a billion vectors. ANN keeps queries roughly **logarithmic** — barely slower as data explodes.

> The whole design tension of a vector DB is right here: **components 2 and 4 exist to escape the brute-force cost that component 3 would otherwise incur.** Everything is in service of *fast similarity search that doesn't fall apart at scale.*

## 4. Distance metrics: how "similar" is measured

### 📄 FROM THE PDF
> …often using distance metrics like **cosine similarity** or **Euclidean distance**.

### 🧠 EXPLAINED
A **distance metric** (or *similarity metric*) is the exact formula the DB uses to score "how close are these two vectors?" You met **cosine similarity** in W2·SG03; here's the fuller picture, because *choosing the metric is a real configuration decision* when you create a collection.

> 🔑 **Distance metric** = the rule for turning "two vectors" into "one number saying how alike they are." The DB ranks results by this number.

The three you'll actually meet:

| Metric | Measures | Intuition | When used |
|---|---|---|---|
| **Cosine similarity** | The **angle** between two vectors (ignores length) | "Do they point the same *direction*?" — same *meaning*, regardless of magnitude | **The default for text embeddings.** |
| **Euclidean distance (L2)** | Straight-line **distance** between the two points | "How far apart are the tips?" (ruler distance) | Image embeddings; when magnitude matters |
| **Dot product** | Direction *and* magnitude combined | Like cosine but *rewards* longer vectors too | Some recommendation setups; when vectors aren't normalized |

> 🔑 **Euclidean distance (L2)** = ordinary straight-line distance, the Pythagorean `√Σ(aᵢ−bᵢ)²`. *Smaller = more similar* (0 = identical point). Contrast cosine, where *larger = more similar* (1 = identical direction).

💻 **The key intuition — angle vs length.** Imagine two arrows from the origin. **Cosine** asks *"are they pointing the same way?"* and ignores how long they are. **Euclidean** asks *"how far apart are their tips?"* — so length matters. For text, we usually care about *direction* (meaning), not *magnitude* (which often just tracks document length), which is why **cosine is the text default.** Fun fact: if all vectors are **normalized** to length 1, cosine and Euclidean rank results *identically* — the choice only bites on un-normalized vectors.

⚠️ **The one rule you must not break:** you must **use the same metric at query time that the index was built with**, and the query vector must come from the **same embedding model** as the stored vectors — otherwise "distance" is comparing apples to a different coordinate system, and results are garbage. (Same-space rule from SG01·§7.3.)

## 5. ANN & indexing: the trick that makes it fast (HNSW)

### 📄 FROM THE PDF
> **Indexing:** Techniques like **Approximate Nearest Neighbor (ANN)** search reduce computational overhead by focusing on approximate rather than exact matches.
> *(and from "How Do Vector Databases Work?)* … Indexing algorithms like **HNSW (Hierarchical Navigable Small World)** ensure fast retrieval.

### 🧠 EXPLAINED
This is the concept that separates "I know what a vector DB is for" from "I know how one works." Slow down here.

**The problem.** Finding the *true* nearest neighbor requires comparing your query to **every** stored vector — that's **exact / brute-force k-NN**, and it costs O(N) per query. At a billion vectors, that's a billion distance computations *per search*. Unusable.

> 🔑 **Exact (brute-force) k-NN** = compare the query to all N vectors, return the true K closest. Perfectly accurate, hopelessly slow at scale.
> 🔑 **Approximate Nearest Neighbor (ANN)** = clever indexes that return the *probably*-closest vectors while examining only a tiny fraction of the data. **You trade a sliver of accuracy for orders-of-magnitude speed.**

**The trade you're making.** ANN might return 9 of the true top-10 instead of all 10 — but do it 1000× faster. That "9 of 10" is called **recall**. For search/RAG, ~95–99% recall is invisible to users and absolutely worth the speedup.

> 🔑 **Recall (in ANN)** = the fraction of the *true* nearest neighbors that the approximate search actually found. The knob you tune: higher recall ↔ slower queries.

💻 **The analogy that nails it — approximate is a *feature*, not a bug.** You already accept approximate-for-speed everywhere: a **bloom filter** says "probably present" to avoid a disk hit; a **cache** serves slightly-stale data to avoid a DB round-trip; **load balancers** use "power of two random choices" instead of truly checking every server. ANN is the same bargain: *give up provable perfection to win enormous speed*, where the tiny error doesn't matter.

**HNSW — the intuition (you don't need the math).** **Hierarchical Navigable Small World** is *the* dominant ANN index. Picture it as a **skip-list for geometry**, or an *express-train map*:

```
  Layer 2 (few nodes, long hops)      A ─────────────► F
                                       │                │
  Layer 1 (more nodes, medium hops)   A ──► C ──► D ──► F
                                       │         │      │
  Layer 0 (ALL nodes, short hops)     A─B─C─D─E─F─G─H─I…   ← every vector lives here
```

- Start at the **top layer** (sparse, long-range links) and greedily hop toward the query — covering huge distance in a few jumps.
- Drop down a layer, refine with medium hops. Drop again, refine with short hops.
- Land at the bottom layer near the true neighborhood and pick the K closest.

You navigate from "roughly the right continent" to "the right street" in a handful of steps, touching a *tiny* fraction of nodes — that's how it stays roughly **O(log N)** instead of O(N).

💻 **Java analogy:** it's a **`SkipList` generalized from 1-D order to N-D geometry.** A skip-list uses express lanes to binary-search a linked list; HNSW uses sparse upper layers as express lanes across a *proximity graph*. Same "shortcut layers for fast navigation" idea.

*(Other indexes exist — **IVF** partitions vectors into clusters and only searches the nearest few; **product quantization** compresses vectors to save memory. HNSW is the one to know first.)*

## 6. Popular vector databases and tools

### 📄 FROM THE PDF
> **Popular Vector Databases and Tools**
> - **Pinecone:** A managed vector database service that's developer-friendly and scalable.
> - **ChromaDB:** Lightweight, open-source, and highly efficient for embedding-based applications.
> - **Qdrant:** Open-source with a focus on scalable and production-ready vector search.
> - **FAISS (Facebook AI Similarity Search):** A library optimized for efficient similarity search and clustering.
> Each of these tools caters to different needs, offering unique features and integrations.

### 🧠 EXPLAINED
The PDF lists four but doesn't give you the *axis* that actually distinguishes them. The axis is **deployment model** — the same "managed vs self-hosted vs embedded" choice you already make for any datastore (RDS vs. running Postgres yourself vs. SQLite):

| Tool | What it is | 💻 Backend analogue | Reach for it when… |
|---|---|---|---|
| **FAISS** | A **library** you call in-process (no server) | **Lucene / SQLite** — embedded, in your app | You want raw speed in a script/notebook; no infra; you'll manage persistence yourself |
| **ChromaDB** | **Lightweight open-source** DB; runs embedded or as a local server | **SQLite → a small local server** | Prototyping, tutorials, small/medium RAG apps (this is the course's default) |
| **Qdrant** | **Open-source, production-grade** server | **Self-hosted Postgres** | You want production features (filtering, sharding) but control your own infra |
| **Pinecone** | **Fully managed** cloud service | **DynamoDB / RDS** — someone else runs it | You want zero ops, elastic scale, and will pay for it |

> 🔑 **FAISS** is a *library*, not a database — it's an in-memory index with no server, persistence layer, or metadata store out of the box. The others are *databases* (they add storage, metadata/filtering, an API). This is why the PDF calls FAISS "a library" and the rest "databases/services." (Chroma and Qdrant even use FAISS-style indexes *under the hood*.)

**Note this repo's continuity:** SG01 already name-dropped **FAISS** and **ChromaDB**; W2·SG03's glossary listed **Pinecone, FAISS, Chroma, pgvector.** Same cast, now with the deployment axis to tell them apart. (Also worth knowing: **pgvector** — a Postgres *extension* — lets your existing SQL database do vector search, so you don't add new infra at all.)

## 7. How a vector DB works — the 4-step lifecycle

### 📄 FROM THE PDF
> **How Do Vector Databases Work?**
> The magic lies in their ability to efficiently compute distances between vectors. Here's a simplified breakdown:
> 1. **Data Ingestion:** High-dimensional vectors are generated (often by models like **SBERT** for text or **CLIP** for images) and stored.
> 2. **Index Creation:** Indexing algorithms like **HNSW (Hierarchical Navigable Small World)** ensure fast retrieval.
> 3. **Query Execution:** When a query is made, the database retrieves vectors closest to the query vector using distance metrics.
> 4. **Post-processing:** Results are filtered or ranked based on additional criteria.

### 🧠 EXPLAINED
Map this straight onto SG01's RAG flow — it's the *inside* of that pipeline's retrieve half:

```
   ┌─────────── INDEX TIME (offline, once) ───────────┐   ┌──── QUERY TIME (per request) ────┐
   ①  DATA INGESTION            ②  INDEX CREATION       │   ③  QUERY EXECUTION      ④ POST-PROCESS
   text/image → embed (SBERT/   build HNSW graph over    │   embed the query →       filter by metadata,
   CLIP) → upsert {id,vec,meta}  the stored vectors       │   ANN top-K nearest       re-rank, format
```

**① Data Ingestion (a.k.a. upsert).** You generate embeddings and load them in with their metadata.
> 🔑 **Upsert** = insert-or-update in one call (the standard vector-DB write op). 🔑 **SBERT (Sentence-BERT)** = a BERT variant fine-tuned to produce one good embedding *per sentence/passage* (plain BERT wasn't built for whole-sentence vectors) — the go-to text embedder for retrieval. **CLIP** (from W2·SG03) does the same for images/text in a shared space.

**② Index Creation.** The DB builds the **HNSW** (or IVF, etc.) index over those vectors — the one-time cost that buys fast queries forever after. 💻 Exactly like `CREATE INDEX` on a SQL table: pay once at build, save on every read.

**③ Query Execution.** Embed the incoming query (same model!), then walk the ANN index to fetch the **top-K** nearest by the chosen **distance metric.** This is the millisecond magic.

**④ Post-processing.** Refine the raw hits: **metadata filtering** (`only docs where tenant = X and date > 2024`), **re-ranking** (a sharper model reorders — SG01·§7.5), dedup, formatting.
> 🔑 **Metadata filtering** = narrowing results by structured attributes stored alongside each vector. 💻 It's the `WHERE` clause bolted onto a similarity search — "nearest neighbors, *but only these tenants/dates/languages.*" Crucial for multi-tenant and permissioned RAG.

Steps ①–② are **index time** (offline, batch); ③–④ are **query time** (live) — the two-clocks split from SG01·§7.3, now concrete.

## 8. The ChromaDB tutorial (the PDF's sample code)

> ✅ **This is the real thing.** The PDF's final line — *"Sample Code: ChromaDB tutorial code"* — pointed at a Colab notebook. That notebook is now captured as a runnable, locally-friendly script: **`week3/code/chromadb_tutorial_demo.py`** (no API key — it runs on open-source models on your machine). Each part of the script is labelled with the section here it demonstrates. Below is the minimal core; the script adds persistence, custom embedders, and full CRUD.

```python
import chromadb
from sentence_transformers import SentenceTransformer

# ── (Optional) see "similarity" for what it is: just a number between two vectors ──
model = SentenceTransformer("all-MiniLM-L6-v2")           # a 384-dim SBERT model (§7①)
emb = model.encode(["The weather is lovely today.", "It's so sunny outside!"])
print(model.similarity(emb, emb))   # cosine similarity matrix, diagonal = 1.0  (§4)

# ── The core vector-DB loop: client → collection → add → query ──
client = chromadb.Client()                                 # in-memory (ephemeral) client
collection = client.create_collection(name="my_collection")# a "table" for vectors

# DATA INGESTION — pass TEXT, no embedder given → Chroma uses its DEFAULT MiniLM to embed
collection.add(
    documents=["This is a document about pineapple",
               "This is a document about oranges"],
    ids=["id1", "id2"],
)

# QUERY EXECUTION — Chroma embeds the query, returns top-K nearest by distance
results = collection.query(
    query_texts=["This is a query document about hawaii"],  # Chroma embeds this for you
    n_results=2,                                            # <-- top-K
)
print(results["documents"])   # 'pineapple' ranks ABOVE 'oranges' — the word "hawaii"
                              # is in NEITHER doc; it matches by MEANING (semantic search)
```

**What each line demonstrates from this guide:** `SentenceTransformer` + `.similarity()` shows the *distance metric* (§4) in the raw; `create_collection` makes the store (and can pick the metric via `metadata={"hnsw:space": "cosine"}`); `add` is *ingestion* + auto-*embedding* (§7①); Chroma builds the *HNSW/ANN index* behind the scenes (§5); `query` runs *top-K nearest* (§7③). The killer detail: **"hawaii" appears in neither stored document, yet the pineapple doc wins** — that's semantic search matching by *meaning*, exactly SG02 §1. And notice you never wrote a distance formula or an index — the DB hides all of §4–§5. **That convenience is the whole point of a vector DB over hand-rolling FAISS.**

**The full script also covers** (see `week3/code/chromadb_tutorial_demo.py`): `PersistentClient` (data survives a restart — what makes it a real DB, §6); pinning your **own** `SentenceTransformerEmbeddingFunction`; choosing the metric with `hnsw:space` (§4); storing **pre-computed** vectors via `embeddings=` (which *bypasses* the embedder); `where={...}` **metadata filtering** with `$eq/$ne/$gt/$in/...` operators (§7④); and **upsert/delete** for full CRUD.

💻 **Java framing:** `client` ≈ a `DataSource`/connection, `collection` ≈ a repository/table, `add` ≈ `saveAll(...)`, `query` ≈ a derived finder like `findTopKNearest(queryText, k, filter)`, `where={...}` ≈ the `WHERE` clause, `upsert`/`delete` ≈ the same JPA ops. Same DAO shape you know — the twist is the "find" is *by meaning*, not by column equality.

## 9. Conclusion & the future (hybrid search)

### 📄 FROM THE PDF
> **Conclusion**
> With advancements in Generative AI, multimodal learning, and autonomous systems, vector databases will become even more integral. Innovations in **hybrid search** (combining text and vector-based retrieval) and tighter integration with large-scale AI models will further expand their utility.

### 🧠 EXPLAINED
The one forward-looking term to bank here is **hybrid search** (you saw it flagged in SG01·§7.5; here's the definition):

> 🔑 **Hybrid search** = combining **semantic** (vector/embedding) search with **lexical/keyword** search (e.g. **BM25**), then merging the two rankings. You get the best of both: semantics catches *"car" ≈ "automobile"* (meaning), keywords nail *exact* tokens like part numbers, error codes, or names that embeddings blur together.

💻 **Why you'll want it:** pure vector search is great at *concepts* but can fumble *exact strings* ("find order **#A1B2-9**" — the embedding doesn't care about the precise code). Pure keyword search is the opposite. Hybrid = run both, blend scores. 💻 Like querying **Elasticsearch (keyword) and your vector index in parallel and reconciling the two result lists.** Expect this to be a standard production RAG upgrade.

The rest of the conclusion is the same trajectory as SG01's ending: vector DBs are becoming core infrastructure for GenAI, multimodal apps, and agents — because *everything* those systems do reduces to "find the relevant vectors, fast."

## 10. Deep dives beyond the PDF

### 10.1 The curse of dimensionality — *why* similarity search is genuinely hard
> 🔑 **Curse of dimensionality** = in very high-dimensional space, geometry gets weird: points spread out so much that *everything becomes roughly equidistant* from everything else, and space-partitioning tricks that work in 2-D/3-D (like a k-d tree) collapse to no-better-than-brute-force.

This is the *deep* reason the PDF's "traditional databases struggle" is true, and *why ANN had to be invented.* You can't just build a spatial tree like you would for map coordinates — at 1,536 dimensions those trees stop pruning anything. HNSW's *graph* approach sidesteps the curse by navigating proximity links rather than partitioning space. Knowing this term signals you actually understand the problem, not just the tooling.

### 10.2 The three tuning knobs you'll actually touch
- **K** (how many neighbors to fetch) — SG01's top-K; too low misses context, too high adds noise + tokens.
- **Distance metric** — cosine for text, usually. Set it at collection creation; changing it later means re-indexing.
- **ANN recall vs speed** (e.g. HNSW's `ef_search`) — turn it up for accuracy, down for latency. This is the exact "9-of-10 vs 10-of-10" dial from §5.

### 10.3 Metadata is a first-class citizen, not an afterthought
Real RAG almost always needs `where` filters: per-user permissions, tenant isolation, date ranges, source type. A vector DB that filters *efficiently alongside* the ANN search (pre- or post-filtering) is a big practical differentiator — it's why "just use FAISS" often isn't enough for production, and Qdrant/Pinecone/Chroma earn their keep.

### 10.4 Vector DB vs. plain embeddings-in-a-list
Early prototypes sometimes keep embeddings in a Python list and `numpy`-loop the distances. That's *exact brute-force k-NN* and it's *fine* up to a few thousand vectors. The vector DB earns its complexity when you cross into tens of thousands+ or need persistence, filtering, and concurrency. Don't over-engineer a 200-doc demo.

## 12. ⚡ 60-second recap

- **Vector DB = a datastore built for one question:** "which stored vectors are nearest this query vector?" — fast, at billions of vectors. It's the engine behind RAG's **retriever.**
- **Why not a normal DB:** B-trees sort scalars for exact/range lookups; similarity is a *distance in high-D space* with no axis to sort on, so naive search = full scan. 💻 Same reason you use **Elasticsearch for text** — a purpose-built index. Vector DB = "Elasticsearch for meaning."
- **4 components:** storage · **indexing (ANN)** · querying (top-K by a distance metric) · scalability. Indexing + scalability exist to dodge brute-force cost.
- **Distance metrics:** **cosine** (angle → meaning; the text default), **Euclidean/L2** (straight-line distance), **dot product** (angle + magnitude). Must match the index; query must use the *same embedding model.*
- **The key trick — ANN:** trade a sliver of accuracy (**recall**) for orders-of-magnitude speed. **HNSW** = a skip-list for geometry: sparse top layers for long hops, dense bottom for precision → ~O(log N).
- **Tools by deployment:** **FAISS** (library, embedded) · **ChromaDB** (lightweight OSS, course default) · **Qdrant** (prod OSS server) · **Pinecone** (managed cloud). Plus **pgvector** (Postgres extension).
- **Lifecycle:** ① ingest/upsert (SBERT/CLIP) → ② build HNSW index → ③ ANN top-K query → ④ post-process (metadata filter, re-rank). ①–② index-time, ③–④ query-time.
- **Future:** **hybrid search** = semantic + keyword (BM25) merged — concepts *and* exact strings.

## 13. 🗂️ Jargon Dictionary

*(New this reading. Reused without redefining — from W2·SG03: embedding, vector, cosine similarity, semantic search, nearest-neighbor search, CLIP, dimension, vector database, Pinecone, FAISS, ChromaDB, pgvector. From SG01: top-K, chunk, index-time vs query-time, hybrid search, re-ranking, retriever.)*

| Term | Definition |
|---|---|
| **Vector database** | A datastore optimized to store embeddings and answer "top-K nearest to this vector" fast, at scale. (Deeper treatment than the W2·SG03 one-liner.) |
| **Unstructured data** | Data with no fixed table schema — free text, images, audio, video. |
| **High-dimensional vector** | A vector with hundreds/thousands of numbers (e.g. 1,536-dim); one point in that many-D space. |
| **Distance metric / similarity metric** | The formula scoring how alike two vectors are; results are ranked by it. |
| **Euclidean distance (L2)** | Straight-line distance between two points, `√Σ(aᵢ−bᵢ)²`; *smaller = more similar.* |
| **Dot product** | Similarity combining direction *and* magnitude (rewards longer vectors); used when vectors aren't normalized. |
| **Normalized vector** | A vector scaled to length 1; makes cosine and Euclidean rank results identically. |
| **Exact / brute-force k-NN** | Compare the query to all N vectors for the true K closest — accurate but O(N), too slow at scale. |
| **Approximate Nearest Neighbor (ANN)** | Index that returns *probably*-closest vectors while checking a tiny fraction of data — trades a little accuracy for huge speed. |
| **Recall (ANN)** | Fraction of the *true* nearest neighbors the approximate search actually returned; the accuracy⇄speed knob. |
| **HNSW (Hierarchical Navigable Small World)** | The dominant ANN index: a layered proximity graph ("skip-list for geometry") giving ~O(log N) search. |
| **IVF (Inverted File Index)** | ANN approach that clusters vectors and searches only the nearest clusters. |
| **Curse of dimensionality** | In high-D space points become near-equidistant and space-partitioning trees fail — the reason ANN graphs are needed. |
| **Upsert** | Insert-or-update in one operation; the standard vector-DB write. |
| **SBERT (Sentence-BERT)** | BERT variant fine-tuned to produce one strong embedding per sentence/passage; a go-to text embedder for retrieval. |
| **Metadata filtering** | Narrowing similarity results by structured attributes (tenant, date, source) — a `WHERE` clause on nearest-neighbor search. |
| **Post-processing** | Refining raw hits: filtering, re-ranking, dedup, formatting. |
| **Data ingestion** | The pipeline of generating embeddings and loading them (with metadata) into the DB. |
| **Qdrant** | Open-source, production-grade vector database (self-hosted server). |
| **Managed vs self-hosted vs embedded** | Deployment axis: Pinecone (managed cloud) · Qdrant/Chroma-server (self-hosted) · FAISS/SQLite-like (embedded library). |
| **BM25** | Classic keyword-ranking algorithm; the "lexical" half of hybrid search. |
